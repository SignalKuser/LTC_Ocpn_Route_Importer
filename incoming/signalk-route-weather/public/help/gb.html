OpenCPN, 32-bit version for Windows
Signal K, Raspberry Pi ARM64

Signal K Preparation

The Signal K plugin (LTC_Ocpn_Route_Importer) can use local GPX files stored on Windows or a Raspberry Pi. However, a more elegant approach is to plot the route in OpenCPN and send it to Signal K "on the fly."

To do this, create a user named "opencpn" in Signal K with read/write permissions, and then generate a token using the following command in the Raspberry Pi terminal:

signalk-generate-token -u opencpn -e 1y -s ~/.signalk/security.json

This is necessary to allow Signal K to accept data from OpenCPN. Keep a copy of the token for later use.

LTC_Ocpn_Route_Importer Installation

It is best to place the PowerShell script in the same folder as the plugin and run it from there. The script will automatically locate the plugin and the Signal K plugin directory on the Raspberry Pi and perform the installation. If Signal K is already running, restart it, then go to the Signal K plugin configuration and set it to "enable." The plugin itself can be accessed via the Webapps section.

Additional Installations

Raster provider: To read GRIB files, the Raspberry Pi requires "grib_get." Therefore, if the Raspberry Pi has internet access, run the following commands in the terminal:

sudo apt-get update
sudo apt-get install libeccodes-tools
sudo apt-get install bzip2  # DWD
sudo apt-get install python3-gdal  # Met Office UKV (NetCDF)

OpenCPN configuration

Direct route import from OpenCPN requires the external OpenCPN plugin Signal K Route Sender.

GitHub release containing Signal K Route Sender

Under Assets, download and extract the RAR archive. In OpenCPN, use Plugins → Import Plugin to install the matching SignalKRouteSender-*.tar.gz package, then enable the plugin.

Under Options → Connections, set up and enable the Signal K connection. If the server requires authentication, enter the Signal K token under Advanced → Auth Token in that connection. The sender uses this connection.

Using OpenCPN

Draw a route in OpenCPN. Right-click on a waypoint or the route itself to open the context menu, and—ideally—assign a name via the "Properties" option. Then, select "Send to Signal K" under the route options at the bottom. The GPX route will be transmitted to Signal K and stored at /signalk/v2/api/resources/routes. Other Signal K plugins (such as Freeboard-SK, Binnacle, etc.) also store their routes here; these can likewise be used with the LTC_Ocpn_Route_Importer.

Using LTC_Ocpn_Route_Importer

On page 1, choose Signal K, GPX (Win) or GPX (Pi) as the route source. GPX (Win) opens the Windows file picker and supports selecting multiple files. Under GPX (Pi), enter the folder path, click Save folder, then choose a file from the list. If a GPX file contains multiple routes, each can be selected individually. The waypoints will appear at the bottom. Choose a weather provider from the "Provider" menu; various options are available. Some providers offer weather data for specific coordinates at a given time, while others automatically download GRIB files, map the waypoint coordinates to the GRIB data, and determine the weather accordingly.

Downloading weather

The weather data is downloaded, assigned to the waypoints based on time, and saved directly. They can be accessed via "Saved Weather Run."

Saved Weather Run

This section holds multiple versions from the same or different providers. Entries can also be deleted here. This is useful for comparing data from different providers for a specific route.

Planned SOG (Speed Over Ground)

This is the theoretical, assumed speed over ground for a vessel that is not yet underway (used for voyage planning). Once the wind conditions have been assessed, the estimated SOG can be entered here. This serves, in effect, as a preliminary step for calculating the ETA (Estimated Time of Arrival).

ETA Calculation

GPS, SOG, COG

It is best to enable these for ETA calculations. They provide the boat’s position and actual speed over ground (SOG), which already accounts for the effects of wind and current. When GPS, SOG, and COG are active and the ETA is based on GPS data, the app uses the measured SOG and, in combination with the course over ground (COG), calculates the component of that speed acting along the leg to the next waypoint. For later legs, the app uses the applicable speed source or the planned SOG. The current at the current position is already factored into the measured speed over ground. If the "current vector" feature is disabled, the app will not calculate additional current forecasts for subsequent route segments. If no reliable GPS-based SOG is available—and no other speed source is present—the app will use the planned SOG value. To estimate the current based on onboard measurements, both types of motion are required as vectors:

  • SOG and COG indicate the speed and direction of the boat's movement over the ground.
  • Speed through water (STW) and the actual direction of movement through the water indicate how the boat is moving relative to the water. (The vessel's heading can serve as an approximation here, though the estimate becomes less accurate if there is significant leeway due to wind.) The difference between these vectors yields the estimated current. STW alone is not sufficient for this calculation!

Current Vector

When the "current vector" feature is enabled and relevant data is available, the app incorporates HARMONIC and HARMONIC.IDX files into its ETA calculations—provided the speed for a given segment is derived from engine-based SOG, LTC polars, STW, or the planned SOG value. Relevant data: The app checks the IDX files to see if the waypoint coordinates match. It is recommended to store all IDX files in a single folder; the app will automatically search through them recursively to identify the appropriate files, which are then displayed for each individual waypoint. This allows for the use of different IDX files along a single route. IDX files for Europe, the North Sea, the German Bight, the Baltic Sea, etc.: https://github.com/SignalKuser?tab=repositories

For each such segment, the app queries the current at the destination waypoint for the tentatively estimated time of arrival (ETA). Based on this, it calculates the current components acting along and across the segment and uses them to adjust the ETA. A measurement of Speed Through Water (STW) is optional for this purpose. If a segment is based on measured GPS-SOG (Speed Over Ground), the app omits the IDX correction for that segment. When loading a route, the app can still check for and indicate whether relevant current stations are available. This check alone does not alter the ETA.

STW – Speed Through Water

If GPS/SOG data is unavailable, STW (Speed Through Water) can serve as the speed basis for calculating the ETA; speed over ground for future legs is estimated by incorporating the current vector. Without a GPS position, the actual progress along the route remains unknown.

AWS – Apparent Wind Speed

For ETA calculations, the current Signal K wind data is assumed to apply to future route segments. If true wind data is missing, the app derives it from the AWS/AWA (Apparent Wind Speed/Angle) in combination with the boat's speed and heading. The LTC polar data is read-only and cannot be modified.

Use True Heading

When enabled, the app aligns AWS/AWA data using "navigation.headingTrue." Otherwise, it uses COG as an approximation. If available, STW is used for wind calculations derived from AWS/AWA. The "STW – Speed Through Water" setting specifically determines whether STW should also be used as a basis for calculating the ETA. If no heading source is available in Signal K, COG is used as an approximation.

Engine On/Off

Once "Engine On/Off" is activated, the app uses the "motor SOG" (speed over ground under engine power) as the basis for all remaining route segments. In this case, this value takes precedence over GPS-based SOG, LTC polar data, STW, and any planned SOG values. If the current vector is also active (provided suitable IDX files are available), the app adjusts the "motor-SOG" (speed over ground under engine power) for the respective leg.

Polar data

When enabled and a suitable file is selected, polar data determines the estimated speed for each leg of the route. The app uses the expected true wind speed (TWS) and the true wind angle (TWA) relative to the leg to estimate how quickly the boat will progress toward the next waypoint. In the case of a headwind, the calculation can also account for tacking (beating). Example: A 20-nautical-mile leg, based on a planned SOG of 5 knots, would take approximately 4 hours. If the polar data indicates a progress speed of only 4 knots toward the destination due to a headwind, the app calculates a duration of 5 hours. Consequently, the estimated times of arrival (ETAs) for subsequent waypoints—and any associated predicted arrival times—are shifted accordingly. When the engine is active, the "motor-SOG" takes precedence. In sailing mode, valid polar data takes precedence over GPS-based SOG, speed through the water (STW), and the planned SOG value. Therefore, the accuracy of the ETA depends on how well the selected polar data represents the boat's actual performance.

Waypoint Radius

A waypoint is considered reached once the vessel enters the defined radius.

Distance and Bearing to the Next Waypoint

It is possible for the current position to be some distance away from the planned route. In such cases, the system displays the distance and bearing to the nearest waypoint on the route. Once this waypoint is reached, all preceding waypoints are considered passed.

Wind Weighting

The wind data provided by the external source is a forecast. Since locally measured wind data is significantly more accurate, it is incorporated into the calculation. As the distance (in terms of both space and time) from a waypoint increases, the weight given to the "on-board" wind data (the wind vector, comprising speed and direction) decreases, eventually becoming negligible. As the boat approaches a waypoint, the weight of the on-board data increases again.

Boat-Based Wind Range

The 15-level slider controls wind weighting. Level 3 is the default. At either limit, the provider forecast supplies 100% of the wind when enabled and available. The slider determines the extent to which the wind currently measured at the boat’s location influences the ETA calculation. At the boat’s current position, this data carries a 100% weight. As a waypoint lies further along the route—and as the estimated travel time to reach it increases—the forecast from the selected weather provider carries progressively more weight. The distance factor accounts for the fact that wind conditions may differ further ahead, while the travel time factor accounts for the possibility that wind conditions may change by the time of arrival, even if the waypoint is nearby. For each waypoint, the system applies the threshold that is reached first (in relative terms). Once either of these limits is met, the weight of the boat-measured wind drops to 0%.
0.5 nm or 10 min
1 nm or 20 min
2 nm or 30 min
3 nm or 45 min
5 nm or 60 min

From level 6 to 15, each step adds 2 nm and 24 minutes. Level 15 reaches 25 nm or 5 hours.

If the blended wind speed falls below one third of the sum of the two weighted speeds, the higher-weighted source supplies its full wind speed and direction for that waypoint. At equal weights, the onboard wind takes precedence.

Checking Signal K paths

In Signal K, open Data → Browser and search for the path. For the boat’s own data, check that Context is self. Value, Timestamp and Source show the current reading, when it was updated and where it came from.

  • navigation.position — GPS position for route progress, distance and bearing to the next waypoint
  • navigation.speedOverGround — Speed over ground (SOG) for ETA and as an alternative to STW for wind calculation
  • navigation.courseOverGroundTrue — True course over ground (COG) for ETA and as an approximation of boat orientation
  • navigation.speedThroughWater — Speed through water (STW) from the log for ETA and wind calculation
  • navigation.headingTrue — True heading when the heading option is enabled
  • environment.wind.speedApparent — Apparent wind speed (AWS)
  • environment.wind.angleApparent — Apparent wind angle (AWA) relative to the bow
  • environment.wind.speedTrue — True wind speed (TWS)
  • environment.wind.directionTrue — True wind direction, measured from true north

Signal K API endpoints

Append these paths to the Signal K server address to check the API in a browser.

  • /signalk/v1/api/vessels/self/navigation/speedThroughWater — Example onboard reading in m/s
  • /signalk/v2/api/vessels/self/navigation/course — Active route, next waypoint and direction
  • /signalk/v2/api/resources/routes — Routes stored in Signal K
  • /signalk/v2/api/weather/_providers — Registered weather providers
  • /signalk/v2/api/weather/forecasts/point — Forecast for waypoint coordinates

Direct export from qtVlm

On page 2, enable the qtVlm receiver. In qtVlm open Data Exchanger → Send, choose the data type and item, and select Send. The Raspberry Pi discovers the sender automatically. Page 2 shows imported items and any errors.

Both devices need to be on the same local network, such as the boat Pi hotspot. The firewall needs to allow discovery on UDP port 5555 and connections from the Pi to qtVlm on TCP port 5555.

  • Routes appear under the Signal K route source.
  • Pathways appear as routes under the Signal K route source.
  • POIs are saved as Signal K waypoints.
  • POI archives are saved as Signal K waypoints tagged with the archive name.
  • Barrier sets are available as GeoJSON files on page 2.
  • Archived tracks appear as GPX files under GPX (Pi).
  • GRIB files appear under Load GRIB file.

Importing qtVlm routes and POIs requires Python 3 on the Pi. For GPS and wind, enter the Pi IP address and port 10110 under NMEA Connections → Incoming → Network sources → TCP. The boat Pi uses 10.42.0.1 by default. Signal K must output the required NMEA 0183 sentences.

Own GRIB file

  1. On page 2, select Enable qtVlm receiver. Send the GRIB file from qtVlm. The received file appears on page 2.
  2. On page 1, choose Own GRIB file in the provider list and click Load GRIB file below the saved weather run.
  3. Select the file under Saved GRIB files and click Use GRIB file.
  4. Choose any extra fields you need under Additional forecast data. Then click Evaluate GRIB on the right.
  5. Use Additional table columns to show the extra values in the table.

If you already have a file, start at step 2. The dialog lets you upload a file, enter an absolute path on the Pi, or use a direct HTTP(S) download link. Enter a name to save the link as a source.

On page 2, qtVlm direct import lists stored GRIB files with the import date and time. To remove a file, click Delete on the right and confirm.

The file and the resulting weather run are available offline. GRIB extraction on the Pi requires libeccodes-tools.
